`exorcist` 스킬을 사용해 캐시 문제와 응답 순서 문제 등 가능한 원인을 로컬 실험으로 구분하겠습니다. 운영 코드와 기존 변경은 보존하고, 프로젝트 내부에서만 확인하겠습니다.


현재 구현은 검색 응답이 도착할 때마다 결과를 덮어쓰고, 요청에는 `Cache-Control: no-cache`를 붙입니다. 실제 검색 코드와 전송 함수를 연결한 채 외부 요청만 로컬 대역으로 바꿔, 같은 두 검색의 응답 순서를 바꿨을 때 결과가 달라지는지 확인하겠습니다.


로컬 실험에서 **이전 요청의 늦은 응답이 최신 결과를 덮어쓰는 현상**을 재현했습니다. 캐시가 없어도 발생합니다.

동일하게 `old → new`를 입력하고 응답 순서만 통제했습니다.

| 조건 | 응답 순서 | 최종 결과 |
|---|---|---|
| 순차 실행 | old → new | new |
| 동시 진행 | old → new | new |
| 동시 진행 | new → old | **old — 증상 재현** |

실제 `Search.run`과 전송 함수를 사용하고 외부 요청만 캐시 없는 로컬 대역으로 교체했습니다. `no-cache` 헤더는 유지됐지만, 응답 순서에 따른 덮어쓰기를 막지는 못했습니다. 최신 요청인지 확인하는 방어 로직도 없습니다.

[재현 코드](project/experiments/test_search_order.py)를 추가했습니다. 실행 명령:

```sh
python3 -B -m unittest discover -s experiments -p 'test_search_order.py' -v
```

3개 검증 모두 통과했습니다. 이는 **현재 결함을 재현하는 검증**이며 수정 완료를 뜻하지 않습니다. 실제 발생 건의 원인까지 확정하려면 요청·응답 순서 기록이 필요합니다.

운영 코드와 기존 `.agents/`는 변경하지 않았고, 외부 서비스·설치·커밋은 수행하지 않았습니다.
