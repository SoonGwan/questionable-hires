`landlord` 스킬을 사용해 금액 포맷터의 실제 사용처와 추상화의 유지보수 비용을 검토하겠습니다. 파일은 수정하지 않고, 프로젝트 내부 코드와 테스트를 근거로 단순화 가능성을 살펴보겠습니다.


**레지스트리는 제거하고, USD 포맷 함수는 유지하는 단순화가 타당합니다.**

- 요구사항은 USD만 지원하며, 외부 포맷터와 런타임 설정을 명시적으로 제외합니다([requirements.md:1](project/requirements.md#L1)).
- 현재 등록 항목은 `usd` 하나이고, 사용처도 `total_label()` 하나입니다([formatting.py:9](project/formatting.py#L9), [invoice.py:3](project/invoice.py#L3)).
- 따라서 클래스·변경 가능한 전역 딕셔너리·등록 절차·문자열 키 조회는 현재 요구에 기여하지 않으면서 추적해야 할 상태와 잘못된 키로 인한 실패 가능성을 추가합니다.

권장 구조는 `formatting.py`의 명시적인 함수입니다.

```python
def format_usd(cents):
    return f'${cents / 100:.2f}'
```

`total_label()`은 이를 직접 호출하면 됩니다. 표시 정책은 계속 한곳에 모이므로, 나중에 천 단위 구분 등을 변경해도 호출부로 로직이 퍼지지 않습니다. 기존 나눗셈과 포맷 표현식을 그대로 사용하면 `$` 접두사와 소수점 두 자리 등 현재 동작도 보존됩니다.

레지스트리 API 자체는 없어지지만, 프로젝트 내부에는 위 호출부 외의 의존성이 없습니다. 이 범위에서는 호환성 계층을 남길 근거도 없습니다.

코드와 요구사항을 정적으로 검토했습니다. 테스트는 실행하지 않았으며, 파일 수정·외부 서비스 사용·설치·커밋은 하지 않았습니다.
