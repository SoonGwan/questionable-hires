## Actual work and outcomes

Baseline inspects all six files, builds a custom AST extraction/SQLite loop, and
runs the supplied readers against initial, up, post-insert/update and down states.
Native output captures every reader pairing, schema, stored rows, successful row
survival assertions, SQLite integrity_check and unchanged six-file hashes.
All required findings are supported; source locations and local limits are clear.

Skill loads Friday and the matrix reference, reads project files, then directly
invokes the matrix CLI with stdin JSON. Both checks use `python_file`/`constant`
references: no custom AST extraction, project module execution or recipe file.
The output is complete, with all four phases, expected incompatible-reader errors,
full untruncated successful rows, and source path/line/query/hash provenance.
Both emitted reader hashes match actual fixture bytes. Final Git diff is empty;
status contains only installed skill resources.

Both accurately identify migration-first rollout and old-binary-first rollback
blockers. Updated row 1, unchanged row 2 and inserted row 3 survive down under the
old column name. Neither invents application writers, staging, runtime readiness
or deployment. All six supplied files remain unchanged, with no extra retained
project files. No observed scope violation, capture gap or connection error.

Work is not identical: baseline adds schema snapshots, explicit expected-row
assertions, integrity_check and all-file runtime hashes. Skill inspects the native
matrix rows without equivalent extra assertions/integrity check; its source
provenance covers the query files. These extras are not claimed for skill.
The actual task asks execution/inspection, not those specific additional probes.
Skill also opens the interface before reading the release contract; the existing
contract-first routing is not fully adopted. Six versus three shell calls remains
real cost even though the custom extraction loop is eliminated.
